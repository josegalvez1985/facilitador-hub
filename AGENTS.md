## Application rules
- The app is React Native with Expo (SDK 58) and Expo Router; the web version runs through react-native-web from the same code. Do not add DOM-only UI (HTML elements, CSS files, Tailwind); use React Native primitives and `StyleSheet`.
- Install dependencies with `npx expo install <package>` so versions match the Expo SDK. Expo APIs change between SDKs: check https://docs.expo.dev/versions/v58.0.0/ instead of relying on memory.
- Store frontend demonstration state in the shared Facilitadores provider (`src/facilitadores/provider.tsx`), never present it as authenticated or durably saved data.
- Keep content sections in distinct file routes under `src/app/` and use the shared shell (`src/facilitadores/shell.tsx`) for navigation so desktop, web mobile and native stay consistent.
- Navigation is defined by the `nav` array in `shell.tsx`. Add new sections there and they show up in both the desktop sidebar and the mobile **Menú** sheet.
  - The mobile bottom bar is fixed by the user's request: Inicio · Marcar · Menú · Perfil · Salir. Do not add sections to it.
  - Nothing is removed from navigation: every section stays reachable from Menú.
- Never hard-code colors: read them from `useTheme().colors` or build styles with `makeStyles((c) => StyleSheet.create(...))` from `src/facilitadores/theme-provider.tsx`, so the 6 color themes and light/dark mode apply everywhere. New theme colors must keep WCAG AA contrast (the test in `__tests__/app.test.tsx` checks it).
- Dates are always the device's current date: use `src/facilitadores/fechas.ts` (`hoy()`, `fechaLarga()`, `semanaDe()`…), never hard-coded dates or `toLocaleDateString` (Hermes locale support varies).
- The product name is shown as "facilitadores", without a trailing period.
- Profile photo: picked and resized to 256 px in `src/facilitadores/foto-perfil.ts`, stored only on the device (AsyncStorage = localStorage on the PWA) under a per-user key `facilitadores.foto.<USUARIO>`, and exposed as `useApp().foto` / `setFoto()` from the provider. Never upload it to the backend or present it as saved in the account. Show it with `Avatar uri={app.foto}`; the Home greeting uses `AvatarAureola` (theme-colored ring, still when the OS asks to reduce motion).
  - The top bar has no avatar, by the user's request: only the title and the notification bell.
- Notification bell: shows the next class to attend from `mi-agenda` and the current time (`useProximaClase` / `PanelProximaClase` in `src/facilitadores/proxima-clase.tsx`). Its "new" dot clears when the panel is opened and comes back when the next class changes. Never put hard-coded sample notifications there.
- User manual: `docs/manual-usuario.md` is shown in Perfil → Ayuda (`src/facilitadores/ayuda.tsx`). When a change alters what the user sees or does, update the manual and run `npm run manual` to regenerate `src/facilitadores/manual.ts`; never edit `manual.ts` by hand. It is written for facilitators, in the same "vos" Spanish as the app, without technical terms.
- Native modules (`expo-image-picker`, `expo-image-manipulator`, `expo-location`, `expo-sharing`, `react-native-webview`…) need a new APK build after they are added; the web/PWA only needs a dev server restart.
- Chart series colors come only from `colors.chart` in `theme.ts` (the same validated blue / aqua / orange in every theme, with light and dark steps). The theme colors (primary/success/accent) fail colorblind checks as series, so never use them for data marks. Charts always offer the values as text (legend totals, a readout, a table view).
- Manual colors come only from `COLOR_MANUAL` in `src/facilitadores/intervenciones.ts`, which holds the APEX system colors (SER red, HACER green, TENER lilac, CARACTER gray, VISION yellow, CORAJE light blue, LIDERAZGO red). Never hard-code a manual color elsewhere.
- In PL/SQL package bodies, declare constants and types before any procedure or function, or the package won't compile.
- "Next index" means the one after the LAST developed index (highest `NRO_INDICE` with `SI_NO = 'Si'` in that postulación, same manual). It is computed server-side in `PKG_AGENDA_APP_ETHOS` and client-side in `materiales.ts`, with the same rule.
- Keep non-route code out of `src/app/`. Tests live in `__tests__/`.
- Tests use a simulated backend. By default `fetchMock` answers `mi-facilitador` (facilitator 7). Use `responder(...)` for one-off responses, `entrar()` to log in, and `llamadaA('fragmento')` to assert on a request by URL rather than by call order. When the user asks for tests, register every new route in the `routes` map of `__tests__/app.test.tsx`.
- Do not run `npm test` and do not write or update tests unless the user explicitly asks: the suite costs too many tokens. Before finishing a change run only `npm run typecheck` and ESLint on the changed files (`npx eslint <files>`), and say that tests were not run.

## Backend (Oracle APEX / ORDS)
- The app uses the published ORDS module `ethos` (schema `WKSP_FUNDCARAC`, APEX workspace `FUNDCARAC`, same users as the previous system). Login comes from `PKG_AUTH_ETHOS` / `ETHOS_TOKENS`, and the business endpoints validate that same token.
- `sql/README.md` documents the contract and indexes every published endpoint (agendas, intervenciones-crud with latitude/longitude, listas, evaluaciones…). `sql/ords_modulo_ethos_export.sql` is the source of truth for handler signatures, though it was exported truncated.
- `sql/auth_facilitadores.sql` is an unused, unpublished alternative. Do not point the app at the `facilitadores` module, because its tokens are rejected by the `ethos` business endpoints.
- The base URL comes from `EXPO_PUBLIC_API_URL` in `.env` (`https://oracleapex.com/ords/fundcarac/ethos/`). Expo inlines it at build time, so changing it needs a dev server restart with `npx expo start --clear`, or a new APK/PWA build.
- There is one active token per user, shared with the previous system: logging in on one side ends the session on the other. The app handles it as an invalid token: one "Tu sesión se cerró" notice, then back to login.
- Every protected call goes through `authFetch` in `src/facilitadores/auth/api.ts`. Never call `fetch` with an `Authorization` header directly.
- oracleapex.com sits behind an anti-bot filter (Akamai) that leaves unanswered any request whose User-Agent contains "okhttp", which is Android's default. The APK then shows "Sin conexión" while the web works. `api.ts` sends `User-Agent: Facilitadores/<version> (Android)` on native (`IDENTIDAD`): every request to the backend must go through `pedir`/`authFetch`, and the User-Agent must never contain "okhttp".
- The app is edge-to-edge, so Android does not resize the window when the keyboard opens. Screens with inputs need `KeyboardAvoidingView` with `behavior="padding"` on native (the shell already wraps every `(app)` screen; the login has its own).
- Facilitator isolation (mandatory): records of one facilitator or user must never mix with another's.
  - The logged user's `ID_FACILITADOR` is a global session value, mirroring APEX's `SELECT ID_FACILITADOR FROM FACILITADORES WHERE USUARIO = :APP_USER`. Read it from `useSession().facilitador`. It is resolved once per token from `GET mi-facilitador` in `src/facilitadores/auth/facilitador.ts`.
  - Facilitator data endpoints derive the id from the token on the server (`PKG_FACILITADOR_APP_ETHOS`, `sql/facilitador_app_ethos.sql`); the client never sends a facilitator id.
  - If an older endpoint does take `id_facilitador`, send the session id and pass the rows through `soloDelFacilitador()`.
  - If the id is `null` (the user is not a facilitator) or not resolved yet, screens must not request data. Never fall back to listing "all".
  - When a port needs a table structure, package code or response shape that isn't in `sql/`, ask the user for it instead of guessing.
- This app modernizes Oracle APEX app 193573 "Facilitadores", one page at a time. The user provides the APEX page export as the spec. When porting a page:
  - Keep its SQL semantics exactly (filters, grouping, `HAVING`, joins, ordering), and cite the original page in a comment.
  - Reuse a published `ethos` endpoint when one returns what the page needs.
  - Otherwise add a procedure to `PKG_FACILITADOR_APP_ETHOS` in `sql/facilitador_app_ethos.sql` that runs the page's query with the id taken from the token, and publish it as a GET handler with its `Authorization` header parameter. Never call `ORDS.DEFINE_MODULE` there: it would wipe the published module. Call `ORDS.DEFINE_TEMPLATE` only when the template does not exist yet (check `USER_ORDS_TEMPLATES`): on an existing template it replaces it and deletes its handlers, so a route with two methods (GET + POST, GET + PUT) ends up with only the last one. This happened to `mis-facturas`.
  - Backend scripts are run by the user in APEX. Say clearly when a change needs one, and never assume it was run.
  - Add the screen under `src/app/(app)/`, its entry in the `nav` array of `shell.tsx`, and a row in the README "Modernización" table.
  - Pages done so far: 11 Evaluaciones (`/evaluaciones`, `mis-evaluaciones`); 2 Intervención (`/marcar`, `mis-intervenciones/*` in `PKG_INTERVENCIONES_APP_ETHOS`, `sql/intervenciones_app_ethos.sql`); 3 Agenda (`/horarios` "Mi agenda", `mi-agenda` in `PKG_AGENDA_APP_ETHOS`, `sql/agenda_app_ethos.sql`); Mis materiales (`/materiales`, `mis-materiales` in `PKG_MATERIALES_APP_ETHOS`, `sql/materiales_app_ethos.sql`); 4–6 Intervenciones / Días / Manuales (`/intervenciones` "Intervenciones realizadas", `intervenciones-realizadas/*` in `PKG_REALIZADAS_APP_ETHOS`, `sql/intervenciones_realizadas_app_ethos.sql`); 7–8 Historial / Observación (`/historial` "Historial de intervenciones" plus the shared edit sheet `editar-intervencion.tsx`, `historial-intervenciones*` in `PKG_HISTORIAL_APP_ETHOS`, `sql/historial_app_ethos.sql`); Formularios 1, 2 y 3 from the editorial-ethos-app site (`/formularios`, `mis-formularios/*` in `PKG_FORMULARIOS_APP_ETHOS`, `sql/formularios_app_ethos.sql`; drawing in `src/facilitadores/formularios/`, one drawing per form for the jsPDF PDF and the SVG preview/PNG; on Android the preview and PNG run in a WebView (`hoja-nativa.tsx`) because react-native-svg draws on the main thread and froze the app ("no responde"); the logo is a small JPEG so jsPDF doesn't decode a PNG in JS; only the logged facilitator's postulaciones, never the site's all-facilitator endpoints; the "Acuerdo" tab draws the cooperation agreement in `acuerdo.ts`, PDF only (view + download), from `mis-formularios/institucion`). Mis facturas (`/facturas`, `mis-facturas/*` in `PKG_FACTURAS_APP_ETHOS`, `sql/facturas_app_ethos.sql`; same `FACTURAS_FACILITADORES` table the site's admin reviews; "por revisar" = `CANTIDAD = 0`, only those can be edited or deleted; the facilitator takes or picks a photo of the invoice (required on create, uploaded straight to Cloudinary with the signature from `mis-facturas/firma-foto`, through `pedirExterno` in `api.ts`) and enters number, timbrado, date (picked in `selector-fecha.tsx`) and month; no AI reading, by the user's decision; the app never shows cantidad, sueldo or monto). Home KPIs come from `mis-intervenciones/resumen` and `mi-agenda`; the bell's next class also comes from `mi-agenda`. Home birthdays come from `cumpleanios-hoy` (`PKG_FACILITADOR_APP_ETHOS`), the one deliberate exception to facilitator isolation: it must return only the name (`nombre`, `soy_yo`), never birth date, age, ids or any other `FACILITADORES` column.
- Session rules, which are deliberate and must not be "fixed":
  - The token lives only in memory. Never persist it; reopening the app returns to the login.
  - "No network" (`SinConexion`) never ends the session.
  - Token-invalid detection (401, or 200 with `success:false` and a "token inválido/expirado" message) runs before `res.ok`.
  - Remembered credentials are saved only after a successful login, in SecureStore on native and localStorage on the PWA, and logout does not clear them.
- The route guard (`RequiereSesion`) wraps `src/app/(app)/_layout.tsx` once. New protected screens go inside `(app)/` and need no extra checks.
- If `EXPO_PUBLIC_API_URL` is missing or a placeholder, `api.ts` falls back to the `ethos` URL (`API_POR_DEFECTO`).
- ORDS sessions are NOT in Spanish (APEX and SQL Workshop are). Any SQL that turns a date into a day or month name must pass the language explicitly: `TO_CHAR(fecha, 'FMDAY', 'NLS_DATE_LANGUAGE=SPANISH')`. Otherwise a query can return rows in SQL Workshop and none from the app. This is why `V_INSTITUCIONES` (today's classes) came back empty in Marcar. Never modify objects the APEX app uses (views, tables, functions): the user does not want the APEX system affected. Make an app-only copy instead, like `V_INSTITUCIONES_APP_ETHOS` in `sql/intervenciones_app_ethos.sql`, which `PKG_INTERVENCIONES_APP_ETHOS` reads instead of `V_INSTITUCIONES`.
- ORDS answers browser CORS preflights itself. A "blocked by CORS policy" error almost always means a 404 URL (wrong path or unpublished module), not missing CORS. Send DELETE without a body or `Content-Type`, because ORDS answers 400 otherwise.
